# Release notes: commit rules agents must follow

Release notes for each surface (CLI, VS Code extension, Atomize Studio) are generated by `scripts/release-notes.ts` from the squash-merged commit log, filtered to that surface's dependency-closure paths. Full mechanism: [`docs/Releasing.md`](../Releasing.md) and ADR-0063.

When producing a PR, commit, or version bump, follow these rules so the generated notes come out correct:

1. **PR title = release-note line.** Squash-merge makes the PR title the commit subject, which becomes a bullet in the GitHub Release of *every* surface whose dependency closure includes the changed paths. Write Conventional-Commit titles that read well to a user out of context.

2. **Shared-package changes: lead the scope with the shared package.** A change under `packages/atomize-schema`, `packages/atomize-core`, `packages/atomize-ai`, or `packages/atomize-sidecar` fans out to multiple surfaces' notes. Title it `fix(schema): …` / `fix(core): …`, never `fix(studio): …` for work that is really a schema change.

3. **Version bump rides the feature PR** as a `chore(release): bump <surface> to <x.y.z>` commit. That subject is filtered out of the notes. For Studio, bump both `packages/atomize-studio/package.json` and `packages/atomize-studio/src-tauri/tauri.conf.json`.

4. **Per-surface wording:** when one commit needs different wording per surface, or must be hidden from one, add trailers to the commit body:
   - `Release-Note(<surface>): <text>` — override for `cli` | `extension` | `studio`.
   - `Release-Note(<surface>): skip` — drop from that surface's notes.
   - `Release-Note: <text>` — bare, applies to any surface without a scoped trailer.

5. **Do not** reach for PR labels or GitHub's native release-notes generator for this — ADR-0063 rejected both. Paths, not labels, decide which release a change appears in.

6. **Keeping paths in sync:** each `publish-*.yml` passes `--paths` to the script; that list must equal the workflow's own `on.push.paths`. If you change one, change the other.
