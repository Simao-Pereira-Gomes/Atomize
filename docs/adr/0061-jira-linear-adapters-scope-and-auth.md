# Jira/Linear platform adapters: no canonical vocabulary, OAuth over long-lived tokens, per-surface redirect capture

Adding Jira and Linear as platforms (#52) forced a decision `IPlatformAdapter` had been quietly avoiding: `getFieldSchemas` was typed to return `ADoFieldSchema[]` directly (`platforms/interfaces/field-schema.interface.ts`), and Templates reference raw Azure-DevOps-native type strings like `"User Story"` (`work-item.interface.ts:73`) throughout filters, mock data, and the schema itself, with ~16 consumers across the CLI wizards, validation, and `template metadata` depending on that shape. Adding a second platform makes that ADO-specific typing incoherent.

**Templates stay platform-specific — no canonical type/field vocabulary, no automatic template portability.** A Jira Template says `workItemTypes: ["Story"]` in Jira's own vocabulary; an Azure DevOps Template keeps saying `["User Story"]`. Atomize does not attempt to make one Template run unchanged against multiple platforms. A canonical taxonomy (`story`, `bug`, `epic`… with adapters translating to/from it) was considered and rejected: nobody has asked for template portability, #52's own motivation is reach (supporting teams not on Azure DevOps), not portability, and a full taxonomy plus a migration of every existing built-in Template is a much larger and more speculative effort than the problem actually in front of us. Portability, to the extent it's ever needed, stays exactly what it already is today: clone an existing Template (`template create --from <name>`, Studio's Catalog Clone) and hand-edit it for the new platform. A dedicated `template convert` command with automated field-mapping was also considered and rejected for the same reason — real implementation cost solving a problem with no evidence anyone has it yet.

What *does* need to change: `getFieldSchemas`'s return type is renamed and regeneralized from `ADoFieldSchema` to a platform-agnostic `FieldSchema` — the shape itself (`referenceName`/`name`/`type`/`isCustom`/`isReadOnly`/`isMultiline`/`isPicklist`/`allowedValues`) is already reasonably generic, so this is a rename-and-consumer-update, not a redesign. Each adapter supplies its own concrete field list through that same shape; no cross-platform field-mapping logic is needed since no Template ever needs to mean the same thing on two platforms. Templates also gain an optional `platform` field (defaulting to `azure-devops` for backward compatibility with every existing Template), so `template list`/the Catalog Browser can label and filter by platform, and `generate` can fail clearly ("this Template targets Azure DevOps, you're connected to Jira") instead of surfacing a confusing runtime error about an unrecognized work item type.

**Scope is Jira and Linear, Jira first** (matching the sequencing #52 already specified as "Linear (priority 2)"), not Jira and GitHub Issues despite `PlatformType`/`PlatformFactory` already having stub cases for `"jira"` and `"github"` — those stubs date to the original 2.0.0 Changelog's "Planned" list (GitHub Issues + Jira Cloud) and predate #52's later replacement of GitHub with Linear based on updated market reasoning. The stale `"github"` stub is left as-is; cleaning it up is out of scope here.

**Jira authentication is OAuth 2.0, not a long-lived API token**, despite API tokens being structurally simpler (they'd reuse the existing `ConnectionProfile`/PAT pattern almost exactly). This is a deliberate security choice: short-lived, revocable, individually-scoped OAuth tokens are preferred over static long-lived credentials, consistent with Atomize's existing security-conscious posture elsewhere (explicit `--insecure-storage` opt-in, Live Execution Confirmation). OAuth's Authorization Code flow needs a redirect target, and *how* each surface captures that redirect differs by necessity:

- **CLI and Studio** (both native processes) use a shared local loopback HTTP server (`http://127.0.0.1:<port>/callback`): open the system browser to the platform's auth URL, capture the authorization code when it redirects back, exchange it for a token. The standard pattern (`gh auth login`, `gcloud auth login`, `aws sso login`).
- **The VS Code extension cannot use the same approach.** A loopback server breaks for anyone running VS Code remotely (SSH Remote, Codespaces, WSL) — the browser on the user's actual machine can't reach a port bound inside the remote environment without VS Code's own port-forwarding. The extension instead uses the `vscode.authentication` API with a registered `UriHandler` (`vscode://<publisher>.<extension>/callback`), VS Code's purpose-built mechanism for exactly this case, and the Marketplace-expected pattern for extension OAuth.

Token exchange and refresh (HTTP calls to the platform's token endpoint) are platform-agnostic and live once in each adapter; only redirect capture is surface-specific. `ConnectionProfile` gains a `JiraProfile` variant carrying `accessToken`/`refreshToken`/`expiresAt` in place of a single static token, stored through the same keychain infrastructure as Azure DevOps PATs.

Linear's auth mechanism (API key vs. an equivalent OAuth flow) needs verifying against Linear's actual API capabilities at implementation time — apply the same OAuth-over-long-lived-token preference if a suitable flow exists for individual/personal use, falling back to API key only if it doesn't. Both Jira and Linear OAuth require registering an OAuth application with Atlassian and Linear respectively (client ID, redirect URI allowlisting) before either integration can function end-to-end — a real external prerequisite, not just code.

## Considered Options

- **Canonical type/field taxonomy with adapter-side translation** — true one-Template-many-platforms portability; rejected as solving a larger, more speculative problem than #52's actual motivation, and as a large migration for every existing built-in Template.
- **Dedicated `template convert` command with automated field mapping** — real implementation cost (mapping logic, review UI across CLI and Studio) for a need with no evidence yet; the existing clone-and-edit workflow already covers the manual case.
- **Jira API token only** — simpler (reuses the PAT pattern exactly), but a static long-lived credential where a more secure, revocable option (OAuth) is available.
- **Jira + GitHub Issues** (matching the existing stub) instead of Jira + Linear — rejected in favor of keeping #52's own stated scope and reasoning.

## Consequences

- Every existing built-in Template implicitly targets Azure DevOps; adding the `platform` field (defaulted for backward compatibility) is a small, additive schema change, not a breaking one.
- The ~16 consumers of `ADoFieldSchema`/`getFieldSchemas` need updating to the renamed/regeneralized `FieldSchema` type — mechanical, but real, cross-cutting work (CLI wizards, validation, `template metadata`, Studio's field pickers).
- OAuth requires registering Atomize as an OAuth application with both Atlassian and Linear ahead of implementation — an external, non-code prerequisite with lead time.
- If Linear turns out not to support a workable personal-use OAuth flow, its adapter will fall back to API keys, producing an intentionally inconsistent auth model between the two new platforms — acceptable, since the OAuth preference is about avoiding long-lived credentials where possible, not uniformity for its own sake.
