# Release notes are generated from a path-filtered commit log over each surface's dependency closure

Each of the three release pipelines (ADR-0030, ADR-0031, ADR-0059) publishes a GitHub Release when a version-bump lands on `main`. This ADR covers how those releases' notes are generated.

**Decision.** A shared `scripts/release-notes.ts` renders the notes for a surface from `git log <last surface tag>..HEAD --no-merges`, filtered to the **paths of that surface's full dependency closure** — not just the surface's own package. For the CLI that is `packages/{cli,atomize-core,atomize-schema,atomize-ai}`; for the extension `packages/{vscode-extension,atomize-core,atomize-schema}`; for Studio `packages/{atomize-studio,atomize-sidecar,atomize-core,atomize-schema,atomize-ai}`. Each pipeline passes its own list, which must stay in sync with that workflow's `on.push.paths` trigger.

**A shared-package change intentionally appears in every dependent surface's notes.** A fix in `atomize-schema` is a real change to the CLI, the extension, *and* Studio, so all three releases should mention it. The commit subject is the note text; when a cross-surface commit needs different wording per surface (or should be hidden from one), a `Release-Note(<surface>): <text>` trailer (or `Release-Note(<surface>): skip`) in the commit body overrides it. `chore(release):` version-bump commits are dropped; an otherwise-empty release publishes with a "no user-facing changes" line.

**Rejected: PR labels + GitHub's native `generate_release_notes`.** All three surfaces release off the same `main` at interleaved versions. GitHub's generator lists every merged PR in the tag range and can only *categorize* or *globally exclude* by label — it cannot filter a single release down to the PRs that touched one surface. Getting per-surface notes that way needs a custom script that queries merged PRs and filters by a `surface:*` label that every PR must carry correctly, enforced by a required check. Commit paths carry the same information, never go stale, and need no per-PR labelling discipline. The one thing labels would add — per-surface *wording* on a cross-surface PR — is covered by the `Release-Note` trailer without the standing cost.

The previous inline `git log -- packages/<surface>/` step (CLI and extension only; Studio had none) filtered to the surface's own package, so a shared-package change that triggered a release was invisible in the notes, and a squash-merged version-bump commit surfaced its unrelated subject.
