# Catalog remove logic moves from the CLI into atomize-core, shared with Studio's sidecar

Issue #141's extraction of `atomize-core` (ADR-0038) pulled the Catalog's list/install/save flows out of the CLI, but left `template remove` behind: `packages/cli/src/cli/commands/template/template-remove.command.ts` still performed a raw `fs.rm(item.path)`, guarded by an inline `item.scope !== "user"` check written directly in the CLI's command layer. Issue #133 (Atomize Studio's Catalog Area: browse + remove) needed the same capability reachable through the companion sidecar process (see ADR-0042). Reimplementing the guard-and-delete logic a second time inside `atomize-sidecar` would have created exactly the kind of divergence the `atomize-core` extraction was meant to close off: two independently maintained places that decide whether a Catalog item is removable, free to drift apart the next time either one changes.

**Decision:** `TemplateCatalog.removeUserItem(kind, name)` (`packages/atomize-core/src/services/template/template-catalog.ts`) is the single implementation of Catalog removal. It looks up the item, refuses to remove anything not scoped to `"user"` (built-in and project-scope items are rejected, matching the CLI's existing guard exactly), and deletes the file — attaching `CATALOG_ITEM_NOT_FOUND`/`CATALOG_ITEM_NOT_USER_SCOPED` error codes so callers can branch on the failure without string-matching the message. `TemplateLibrary.removeCatalogItem` exposes it on the library's public surface alongside `findCatalogItem`, `installTemplate`, and `saveTemplate`. The CLI's `template remove` command now calls this method to perform the actual deletion instead of `fs.rm` directly, while keeping its own terminal-specific interactive confirmation (`@clack/prompts`'s `confirm()`) — only the guard-and-delete mechanics needed to be shared; the CLI's y/n prompt and Studio's own type-to-confirm dialog remain separate, surface-appropriate UX built on top of the same shared operation. `atomize-sidecar`'s `catalog.remove` RPC method (`packages/atomize-sidecar/src/protocol.ts`) calls this same `TemplateLibrary.removeCatalogItem`, so the CLI and Studio can never independently decide whether a given item is removable.

**Considered:** implementing the scope guard and delete directly inside `atomize-sidecar`'s `protocol.ts`, leaving the CLI's `fs.rm` call untouched — rejected. It would have shipped a second, sidecar-only deletion path on the same day the sidecar architecture (#143) first existed, and any future change to the removal guard (for example, relaxing it to also permit project-scope removal) would need to be made and tested in two places instead of one.
