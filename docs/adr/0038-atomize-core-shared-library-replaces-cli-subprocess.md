# Atomize core extracted into a shared library, replacing CLI subprocess across the extension and Studio

`@sppg2001/atomize` exposes only a CLI `bin`, no library surface. The VS Code extension and Atomize Studio each talk to it as a subprocess — `node:child_process` and `tauri-plugin-shell` respectively — independently reimplementing presence/version-checking, JSON stdout parsing, and error classification against the CLI's TTY-oriented output contract. ADR-0036 considered and rejected embedding for Studio specifically, on the grounds that this library surface didn't exist and building one was "real, separately-scoped work." This ADR is that work. It's motivated by two costs bundling the CLI binary alone can't fix: per-invocation process-spawn latency, and no persistent state across calls (no warm Azure DevOps client, no cache) — which blocks Studio's planned Live Preview (execute-on-every-input-change, issue #138) from working well under any subprocess shape, bundled or not.

**Decision:** a new `@sppg2001/atomize-core` workspace package is carved out of `packages/cli/src/{services,platforms,core}` — `services`/`platforms`/`core` have zero imports back into `cli/commands` today, so the split has no circular-dependency cost. It exports `Atomizer`, `TemplateLibrary`, and `PlatformFactory`; `PlatformFactory`/`profile-resolver.ts` gain an auth-injection interface so callers supply credentials rather than the module resolving them internally via keytar. The CLI's own command layer is refactored to depend on `atomize-core` instead of importing `src/services` directly, so the CLI is provably the same implementation the other two consumers use, not a fourth divergent copy — its `keychain.service.ts` (keytar + keyfile fallback) is otherwise unchanged, since it works via ordinary npm install resolution. The VS Code extension embeds `atomize-core` directly, in-process, dropping `cli-provider.ts`/`cli-lifecycle.ts` and the `atomize.cliPath`/`atomize.cli.installCommand`/`atomize.cli.autoCheckUpdates` settings entirely; credentials come from `vscode.ExtensionContext.secrets`, injected per call. Atomize Studio stays on Tauri and replaces its per-call CLI subprocess with a long-lived sidecar — a thin server wrapping `atomize-core`, compiled to a standalone binary and bundled via Tauri's `externalBin` mechanism, spawned once at launch rather than once per command. The Rust backend relays every capability through a `tauri::command` over stdio (newline-delimited JSON) rather than exposing a local network server, preserving the app's existing explicit-allowlist security model (`capabilities/default.json`); credentials are resolved by Rust via the `keyring` crate and injected the same way the extension injects them, so the sidecar never touches keytar or OS-keychain access directly. `feat/templateBuilder` — the already-implemented CLI Gate / CLI Bridge MVP (issues #108, #109), unmerged — is held rather than shipped, and Studio is reworked onto the sidecar model before it ships, so the CLI Gate's install-prompt UX never reaches users. This ADR supersedes ADR-0036.

**Considered:** bundling the existing CLI binary as a Tauri sidecar, or as a bundled extension dependency spawned as a subprocess, without a library API — rejected because it only removes install/version-gate friction, not the per-call spawn cost and lack of persistent state Live Preview needs. A full Rust rewrite of the core business logic — rejected as disproportionate: there's no official Azure DevOps SDK for Rust, it forks the validation/schema layer (Studio already depends on `@sppg2001/atomize-schema` directly as pure TS today), and it only avoids adding a third parallel implementation if the published CLI itself becomes the Rust core rather than staying TypeScript alongside it. Switching the Studio shell from Tauri to Electron for direct in-process embedding — rejected: the long-lived sidecar already eliminates the per-call spawn cost and statelessness that motivated this ADR, so Electron's remaining edge is a marginal IPC-serialization saving, not the large win it looks like at first; that's outweighed by Electron's bundled-Chromium footprint and startup/memory cost, and Tauri's Rust investment so far is negligible (`src-tauri/src/lib.rs` is still a stub) so there's nothing to reopen this decision over later without significant new information. Keeping `atomize.cliPath` as an opt-in extension fallback — rejected to avoid two indefinitely-maintained code paths working against the goal of a single shared implementation. Bundling keytar's native binary inside the compiled sidecar executable — rejected as unproven: the CLI's own `build:standalone` script has no `--external keytar` and isn't exercised anywhere in CI or docs, and Studio currently gets a working keytar "for free" only because it subprocess-invokes a separately, globally npm-installed CLI whose `node_modules` resolution already solved the native-binary problem outside Studio's own build. The Studio frontend calling the sidecar's local server directly instead of through Rust — rejected to avoid introducing a local network server (port and token scheme) as new attack surface.
