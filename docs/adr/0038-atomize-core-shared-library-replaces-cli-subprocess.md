# Atomize core extracted into a shared library, replacing CLI subprocess across the extension and Studio

`@sppg2001/atomize` exposes only a CLI `bin`, no library surface. The VS Code extension and Atomize Studio each talk to it as a subprocess — `node:child_process` and `tauri-plugin-shell` respectively — independently reimplementing presence/version-checking, JSON stdout parsing, and error classification against the CLI's TTY-oriented output contract. ADR-0036 considered and rejected embedding for Studio specifically, on the grounds that this library surface didn't exist and building one was "real, separately-scoped work." This ADR is that work. It's motivated by two costs bundling the CLI binary alone can't fix: per-invocation process-spawn latency, and no persistent state across calls (no warm Azure DevOps client, no cache) — which blocks Studio's planned Live Preview (execute-on-every-input-change, issue #138) from working well under any subprocess shape, bundled or not.

**Decision:** a new `@sppg2001/atomize-core` workspace package is carved out of `packages/cli/src/{services,platforms,core,templates,utils}` — the fuller boundary than first scoped: `TemplateLibrary` (one of the three exports below) actually lives in `templates/`, and `core/` depends on `utils/` (graph/estimation-normalizer helpers, themselves thin wrappers over `@sppg2001/atomize-schema`), so both move too. `services`/`platforms`/`core`/`templates` are not quite the zero-import-back-into-CLI claim originally recorded here: two things reach into CLI-owned code today — `config/logger.ts` writes through the CLI's `cli/utilities/terminal-output.ts` formatter, and `config/profile-resolver.ts` imports `validateOrganizationUrl` from a CLI command helper. Both are resolved by the move: `atomize-core` defines its own minimal logger interface (`error/warn/info/debug`) with a package-owned default implementation (no CLI import at all); the CLI keeps its separate terminal-formatted logger for command-layer-only output. `validateOrganizationUrl` moves into `atomize-core` alongside a new pure `buildAzureDevOpsConfig(fields, resolvedToken)` step, replacing what `profile-resolver.ts` did inline. It exports `Atomizer`, `TemplateLibrary`, and `PlatformFactory`. `PlatformFactory.create()` already takes a fully-built `PlatformConfig` today, so the "credential-injection interface" is narrower than it sounds: only the pure, no-I/O slice of profile resolution moves into `atomize-core` (URL validation + config assembly, via `buildAzureDevOpsConfig`, taking a new package-local `AzureDevOpsConnectionFields` type — organizationUrl/project/team, no name, no token). Profile *lookup* and *secret resolution* stay each consumer's own responsibility — CLI keeps `connections.config.ts` + `keychain.service.ts` (keytar + keyfile fallback) unchanged, since they work via ordinary npm install resolution; the extension will use `vscode.ExtensionContext.secrets`; Studio's Rust backend will use the `keyring` crate — each simply calls `buildAzureDevOpsConfig` once it has resolved a profile's fields and secret itself. The CLI's own command layer is refactored to depend on `atomize-core` instead of importing `src/services` directly, so the CLI is provably the same implementation the other two consumers use, not a fourth divergent copy. The VS Code extension embeds `atomize-core` directly, in-process, dropping `cli-provider.ts`/`cli-lifecycle.ts` and the `atomize.cliPath`/`atomize.cli.installCommand`/`atomize.cli.autoCheckUpdates` settings entirely; credentials come from `vscode.ExtensionContext.secrets`, injected per call. Atomize Studio stays on Tauri and replaces its per-call CLI subprocess with a long-lived sidecar — a thin server wrapping `atomize-core`, compiled to a standalone binary and bundled via Tauri's `externalBin` mechanism, spawned once at launch rather than once per command. The Rust backend relays every capability through a `tauri::command` over stdio (newline-delimited JSON) rather than exposing a local network server, preserving the app's existing explicit-allowlist security model (`capabilities/default.json`); credentials are resolved by Rust via the `keyring` crate and injected the same way the extension injects them, so the sidecar never touches keytar or OS-keychain access directly. `feat/templateBuilder` — the already-implemented CLI Gate / CLI Bridge MVP (issues #108, #109), unmerged — is held rather than shipped, and Studio is reworked onto the sidecar model before it ships, so the CLI Gate's install-prompt UX never reaches users. This ADR supersedes ADR-0036.

AI-provider logic (`src/ai/`) is deliberately left out of this extraction: today it has zero dependency from `services`/`platforms`/`core`/`templates` — the CLI command layer generates completion text via `ai-factory.ts` and hands already-generated text to `services/template/llm-template-generator.ts` for parsing, so the seam is already clean. It will likely need the same treatment once a second consumer wants AI-assisted features, but as a separate sibling package (mirroring `atomize-schema`), not folded into `atomize-core` — an AI provider is an independently-varying concern (different credential shape, and `atomize-core` consumers who don't need AI shouldn't pay for the `openai` SDK's weight, which matters for the extension's in-process bundle size). Deferred until a concrete second consumer exists.

**Considered:** bundling the existing CLI binary as a Tauri sidecar, or as a bundled extension dependency spawned as a subprocess, without a library API — rejected because it only removes install/version-gate friction, not the per-call spawn cost and lack of persistent state Live Preview needs. A full Rust rewrite of the core business logic — rejected as disproportionate: there's no official Azure DevOps SDK for Rust, it forks the validation/schema layer (Studio already depends on `@sppg2001/atomize-schema` directly as pure TS today), and it only avoids adding a third parallel implementation if the published CLI itself becomes the Rust core rather than staying TypeScript alongside it. Switching the Studio shell from Tauri to Electron for direct in-process embedding — rejected: the long-lived sidecar already eliminates the per-call spawn cost and statelessness that motivated this ADR, so Electron's remaining edge is a marginal IPC-serialization saving, not the large win it looks like at first; that's outweighed by Electron's bundled-Chromium footprint and startup/memory cost, and Tauri's Rust investment so far is negligible (`src-tauri/src/lib.rs` is still a stub) so there's nothing to reopen this decision over later without significant new information. Keeping `atomize.cliPath` as an opt-in extension fallback — rejected to avoid two indefinitely-maintained code paths working against the goal of a single shared implementation. Bundling keytar's native binary inside the compiled sidecar executable — rejected as unproven: the CLI's own `build:standalone` script has no `--external keytar` and isn't exercised anywhere in CI or docs, and Studio currently gets a working keytar "for free" only because it subprocess-invokes a separately, globally npm-installed CLI whose `node_modules` resolution already solved the native-binary problem outside Studio's own build. The Studio frontend calling the sidecar's local server directly instead of through Rust — rejected to avoid introducing a local network server (port and token scheme) as new attack surface.
