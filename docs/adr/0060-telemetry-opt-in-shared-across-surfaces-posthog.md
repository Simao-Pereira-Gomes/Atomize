# Telemetry is opt-in, shared across all three surfaces, and backed by PostHog

Atomize usage telemetry (#50) is **opt-in**, not opt-out, despite opt-out being the industry default for dev-tool telemetry (`next telemetry`, `dotnet` CLI, Homebrew analytics). Every other privacy/trust-adjacent surface in Atomize requires explicit user action: `--insecure-storage` to use the weaker PAT fallback, a Live Execution Confirmation naming exactly what will be created before any `--execute` run, explicit `--pat-stdin` for non-interactive rotation. Silent-by-default telemetry would break that pattern, and Atomize is used by security-conscious teams against Azure DevOps in environments where unapproved outbound calls from a CLI can be a compliance problem. For the same reason, environment variables (`ATOMIZE_TELEMETRY=0`, `DO_NOT_TRACK=1`) can only turn telemetry **off**, so an organisation can enforce it fleet-wide, while nothing but an explicit, persisted user choice can turn it on.

Consent is invited, never demanded. Each surface shows a **one-time, non-blocking nudge** after the user's first successful action (a hint line in the CLI, a `showInformationMessage` with Enable / Not now / Learn more in VS Code, an inline banner in Studio), rather than a blocking first-run prompt. A blocking prompt would hold the shell after the user's command and break interactive `atomize … && …` chains; we accept a lower opt-in rate as the price of never interrupting.

Consent and the anonymous installation ID are **shared across the CLI, Atomize Studio, and the VS Code extension** through one file, `~/.atomize/telemetry.json`. Opting in once, from any surface, opts in all three, and every consent surface says so. Cross-surface adoption (does a CLI user also pick up Studio or the extension) becomes measurable through one anonymous ID instead of three uncorrelated ones: the original motivation for treating this as a global concept rather than CLI-only. Per-surface enablement was rejected because it would bias that measurement (a CLI-only opt-in makes the same user's Studio use invisible) on top of an already low opt-in rate.

This is a deliberately different call from Connection Profiles, where the extension owns fully independent storage with only a one-time CLI import (ADR-0040) rather than sharing `~/.atomize/connections.json`. That independence was driven by a real cost: sharing profiles would have meant bundling `keytar` (a native module) into the extension just to decrypt shared secrets. Telemetry consent carries no secret and needs no native module, so that cost doesn't apply here.

The extension still respects its own platform's expectations on top of the shared file: it requires `vscode.env.isTelemetryEnabled` to also be true before sending any event or showing its nudge, as VS Code's extension telemetry guide requires, so VS Code's own telemetry switch always wins regardless of the shared file's state.

The anonymous ID is created on first opt-in and **kept when the user disables telemetry**, rather than deleted. Deleting it locally would not erase anything already sent, and would destroy the only key a user has to ask for that data to be erased. Every surface can show the ID and send an in-product deletion request. Sending one does retire the ID, so a later opt-in gets a new one: PostHog warns against reusing a distinct ID queued for deletion, and new events under it could be erased with the old ones or attached to the person the deletion workaround creates.

Events are ingested by **PostHog's hosted free tier in its EU region**, not a self-hosted Cloudflare Worker + KV/D1. Self-hosting would mean building and maintaining an ingestion endpoint, storage, and a dashboard layer from scratch for a solo-maintained project. The EU region keeps the data inside the EU and avoids a transfer question; moving region later would mean a data migration. Events are sent with plain `fetch` (no PostHog SDK, so no autocapture, cookies, or storage), with client IP discarded and GeoIP enrichment disabled, and **without person profiles**. Person profiles fall outside PostHog's events retention and would persist indefinitely, breaking the stated retention limit; the price is that PostHog can only delete personless events after first attaching them to a person, so deletion requests are processed by a scheduled GitHub Action that performs that workaround rather than by hand. Delivery is **fire-and-forget with no retry/offline queue**: a dropped event is simply lost; the goal is trend signal, not a complete record.

Shared logic (event schema, `telemetry.json` read/write, the PostHog client) lives in a new **`atomize-telemetry` package**, matching the existing single-purpose extraction pattern (`atomize-schema`, ADR-0035; `atomize-ai`) rather than folding cross-cutting infrastructure into `atomize-core`'s template/generation domain logic. The CLI and the extension depend on it directly. In Studio it runs in the **sidecar** (ADR-0042), not the webview: the sidecar already has filesystem and network access in the same runtime family as the CLI, whereas the webview, which renders template content, would need its filesystem scope widened to the home directory. The webview reports through the existing sidecar protocol. No event originates in Studio's Rust process: every Rust command is invoked from the webview, which already sees its outcome.

## Considered Options

- **Opt-out with an `ATOMIZE_TELEMETRY=false` env var**: the originally proposed approach; rejected for conflicting with Atomize's existing explicit-consent pattern elsewhere.
- **A blocking first-run prompt**: higher opt-in, but it interrupts the user after their command and blocks interactive shells.
- **Fully independent per-surface consent and anonymous IDs** (including for the extension): simpler, but forecloses cross-surface adoption analysis.
- **Extension consent modeled on ADR-0040's profile independence**: rejected once the actual blocker behind ADR-0040 (native-module bundling cost) was confirmed not to apply to a plain JSON file.
- **Deleting the anonymous ID on disable**: a cleaner break, but it strands the user's already-sent data with no key to request its erasure.
- **PostHog person profiles**: simpler deletion, but profiles outlive events retention and would need their own clean-up.
- **Self-hosted Cloudflare Workers ingestion**: full data ownership, but real ongoing infrastructure for a project that needs to stay easy to maintain.
- **Running Studio's telemetry in the webview, with Rust events relayed into it**: the original plan; rejected because it widens the webview's filesystem scope and the Rust relay carries nothing the webview doesn't already know.

## Consequences

- PostHog is a third-party processor: this is stated in every nudge and on the website's telemetry page, alongside the retention period, a 30-day deletion promise, and a contact address. Retention is stated as "about 12 months, up to about 14", never a flat 12: the free tier's events retention is fixed at 1 year, but PostHog's cleanup runs monthly and only drops a calendar month once all of it has expired, so events can outlive the year by up to about two months, and backups hold event data for about two weeks more (including data already deleted on request). The data counts as pseudonymous personal data under GDPR because the Anonymous ID is persistent, so the stated period has to be accurate. PostHog's DPA must be accepted and its "Discard client IP data" project setting enabled before release.
- Every write to `~/.atomize/telemetry.json` (from any of the three surfaces) must be treated as externally-changeable state by the others: consent is re-checked at send time, and writers re-read and merge rather than overwrite, the same discipline already required of Connection Profile secret resolution across CLI and Studio (ADR-0043).
- The extension honours VS Code's switch only through `vscode.env.isTelemetryEnabled` and `onDidChangeTelemetryEnabled`, which VS Code's extension telemetry guide requires. That flag is true only at telemetry level `all`, so the extension already sends nothing at `error`, `crash`, or `off`; distinguishing those levels individually would only loosen this, and is not required.
