# Telemetry is opt-in, shared across all three surfaces, and backed by PostHog

Atomize usage telemetry (#50) is **opt-in**, not opt-out, despite opt-out being the industry default for dev-tool telemetry (`next telemetry`, `dotnet` CLI, Homebrew analytics). Every other privacy/trust-adjacent surface in Atomize requires explicit user action — `--insecure-storage` to use the weaker PAT fallback, a Live Execution Confirmation naming exactly what will be created before any `--execute` run, explicit `--pat-stdin` for non-interactive rotation. Silent-by-default telemetry would break that pattern, and Atomize is used by security-conscious teams against Azure DevOps in environments where unapproved outbound calls from a CLI can be a compliance problem.

Consent and the anonymous installation ID are **shared across the CLI, Atomize Studio, and the VS Code extension** through one file, `~/.atomize/telemetry.json` (`{ enabled: boolean, anonymousId: string }`). Opting in once, from any surface, opts in all three, and cross-surface adoption (does a CLI user also pick up Studio or the extension) becomes measurable through one anonymous ID instead of three uncorrelated ones — the original motivation for treating this as a global concept rather than CLI-only.

This is a deliberately different call from Connection Profiles, where the extension owns fully independent storage with only a one-time CLI import (ADR-0040) rather than sharing `~/.atomize/connections.json`. That independence was driven by a real cost: sharing profiles would have meant bundling `keytar` (a native module) into the extension just to decrypt shared secrets, hurting package size and activation time. Telemetry consent carries no secret and needs no native module — `~/.atomize/telemetry.json` is a plain boolean-plus-UUID file, trivially read with `fs` — so the specific thing that justified independence for profiles doesn't apply here, and consent is a single ongoing preference a user would reasonably expect to stay consistent everywhere, unlike per-org profile data where re-entry is a one-time onboarding cost.

The extension still respects its own platform's expectations on top of the shared file: it requires `vscode.env.isTelemetryEnabled` to also be true before sending any event — both gates must pass, so VS Code's own telemetry off-switch always wins regardless of the shared file's state (Marketplace policy expects extensions to defer to the editor's own switch, not bypass it). A user who has never touched the CLI or Studio still needs an explicit way to opt in from inside the editor: a one-time activation notification (`vscode.window.showInformationMessage`, Enable / Not now / Learn more) writes `enabled: true` to the shared file exactly as the CLI's first-run prompt would.

Events are ingested by **PostHog's hosted free tier**, not a self-hosted Cloudflare Worker + KV/D1. The payload (command/action name, Atomize version, Node version, OS, anonymous ID — never org URLs, PATs, or Story/Task content) is anonymous regardless of which backend receives it, and self-hosting would mean building and maintaining an ingestion endpoint, storage, and a query/dashboard layer from scratch for a solo-maintained project. Delivery is **fire-and-forget with no retry/offline queue** — a dropped event is simply lost; the goal is trend signal, not a complete record.

Shared logic (event schema, `telemetry.json` read/write, the PostHog client) lives in a new **`atomize-telemetry` package**, matching the existing single-purpose extraction pattern (`atomize-schema`, ADR-0035; `atomize-ai`) rather than folding cross-cutting infrastructure into `atomize-core`'s template/generation domain logic. All three surfaces depend on it directly — the extension already embeds `atomize-core` in-process (ADR-0038), so bundling another lightweight, native-dependency-free JS package is consistent with that existing shape. Studio's Rust process has no direct dependency on it; any telemetry-worthy event originating in Rust (e.g. a keyring operation) crosses the existing sidecar/IPC relay (ADR-0042) into the webview, which reports it through the shared package like any other JS-originated event.

## Considered Options

- **Opt-out with an `ATOMIZE_TELEMETRY=false` env var** — the originally proposed approach; rejected for conflicting with Atomize's existing explicit-consent pattern elsewhere.
- **Fully independent per-surface consent and anonymous IDs** (including for the extension) — simpler, but forecloses cross-surface adoption analysis, one of the more valuable things telemetry could tell a solo maintainer, and loses that value most on the surface — the extension — where it might matter most.
- **Extension consent modeled on ADR-0040's profile independence** — rejected once the actual blocker behind ADR-0040 (native-module bundling cost) was confirmed not to apply to a plain JSON boolean+UUID.
- **Self-hosted Cloudflare Workers ingestion** — full data ownership, but real ongoing infrastructure (endpoint, storage, and a dashboard layer to actually read the data) for a project that needs to stay easy to maintain.

## Consequences

- PostHog is a third-party processor: even though payloads are anonymous, this should be stated plainly in the CLI's opt-in prompt, the extension's activation notification, and the README's telemetry documentation.
- Every write to `~/.atomize/telemetry.json` (from any of the three surfaces) must be treated as externally-changeable state by the others — no surface can assume it's the sole writer, the same discipline already required of Connection Profile secret resolution across CLI and Studio (ADR-0043).
- If VS Code later exposes finer-grained telemetry levels (`vscode.env.telemetryConfiguration`'s `all`/`error`/`crash`/`off`, superseding the boolean `isTelemetryEnabled`), the extension's gate should adopt the finer-grained check rather than staying on the boolean once that API is the recommended one.
