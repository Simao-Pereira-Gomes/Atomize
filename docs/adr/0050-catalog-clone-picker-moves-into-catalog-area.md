# Catalog Clone's picker moves into the Catalog Area instead of a separate inline list

Issue #129 recorded Starting Path as a four-option set — scratch, Catalog Clone, Open, AI draft — each resolving entirely within the Templates Area's own flow. Following that literally, the Catalog Clone tile opened an inline, flat list of Templates rendered inside `StartingPathPicker.tsx` itself. Issue #133 then added a second, independent Catalog Area (browse + remove) reachable from the sidebar, rendering the same underlying Catalog data — Templates and Mixins grouped by scope — through a different component. The result was two screens a user could not tell apart by function: one supported Clone but not Remove or Mixins, the other supported Remove and Mixins but not Clone, and nothing in the UI signaled which was which before you opened it.

**Decision:** the Catalog Area becomes the single place the Catalog is browsed. `StartingPathPicker`'s "Clone from Catalog" tile no longer renders its own list; it calls a new `onBrowseCatalog` prop that switches `StudioShell`'s `activeArea` to `"catalog"`. `CatalogArea` gains a `Clone` action on Template rows (available at any scope — Built-in, User, or Project — matching what the inline picker always allowed, not just User scope, which is Remove's own restriction). Selecting Clone calls back into `StudioShell`, which performs the same `stores.loadTemplate(toCatalogClone(item))` the inline picker used to trigger, then sets both `surface` to `"builder"` and `activeArea` back to `"templates"` so the user lands directly in the authoring surface regardless of which area they clicked Clone from.

This introduces a gap the previous design didn't have: the other three Starting Paths (scratch, Open, AI draft) are only reachable through `StartingPathPicker`, which itself only renders when `surface() === "starting-paths"` — so by the time any of them can fire, `changeStartingPath`'s `stores.reset()` has already cleared whatever was being edited, or nothing was loaded yet. Catalog Area's Clone action has no such guarantee: a user can switch to the Catalog Area from the sidebar while `surface() === "builder"` (Studio Areas are independent and switching between them does not reset in-progress authoring state, by design) and clone a Template directly on top of an active session. `StudioShell` closes this gap itself: `requestCatalogClone` checks `surface()` and, if a builder session is active, shows a discard confirmation (mirroring `AtomizeStudio`'s existing "Back to starting paths?" dialog) before calling through to the actual clone.

**Considered:** keeping both list UIs and only unifying the underlying `CatalogItem` type (the state at the end of #133) — rejected once articulated as a UX problem rather than a code-duplication one: the duplication that mattered wasn't the ~20 lines of list-rendering markup (already trivial), it was two visually and structurally different screens for the same task, forcing the user to already know which one supported what they wanted. Adding a "Clone" action to Catalog Area's rows while also keeping the Starting Path's own inline list as a shortcut — rejected as introducing a third pattern (two ways to reach Clone) instead of resolving the original two-ways-to-browse problem.
