# Bundled atomize-core consumers must supply TemplateCatalog's packageRoot explicitly

`TemplateCatalog` locates its builtin `catalog/` directory by walking up from its own module file (via `import.meta.url`) to the nearest `package.json`. That default only holds for a consumer that runs `atomize-core`'s source unbundled — true for local dev/tests (workspace-linked, real file paths) but not for any consumer that bundles `atomize-core` into a single output file, since bundling erases the module's original on-disk location. Under esbuild's CJS output (the VS Code extension) this throws outright (`import.meta` becomes `{}`, so `fileURLToPath(undefined)` throws); under ESM bundling (the CLI's `dist/cli/index.js`) it silently resolves to the *consumer's own* nearest `package.json` instead of atomize-core's, which is how `packages/cli/catalog` came to exist as a second, manually-maintained copy of `packages/atomize-core/catalog` in the first place (added when atomize-core's catalog was extracted in ADR-0038, without removing the CLI's pre-existing copy) — the two only stayed identical by coincidence.

**Decision:** `packages/atomize-core/catalog` is the single authored copy. Every consumer that bundles `atomize-core` regenerates its own local copy at build time and passes it to `TemplateCatalog` as an explicit `packageRoot` (an option the constructor already accepted), rather than relying on the default resolution:
- The CLI's `scripts/prepare-dist.mjs` copies `../atomize-core/catalog` into `packages/cli/catalog` before bundling; that directory is now gitignored rather than committed, and `validate-package.mjs`'s existing check that it exists post-build is what would catch a missing/failed copy.
- The VS Code extension's `esbuild.mjs` copies `../atomize-core/catalog` into `dist/catalog`, and `src/core-library.ts`'s `createTemplateLibrary()` constructs `TemplateCatalog` with `packageRoot: __dirname` (the bundled `extension.js`'s own directory at runtime) instead of calling `new TemplateLibrary()` directly.
- Atomize Studio's future sidecar (ADR-0038), once it bundles `atomize-core` into a compiled binary, needs the same treatment: copy the catalog alongside the binary at build time and supply `packageRoot` explicitly. `findPackageRoot()`'s default remains fine for unbundled contexts and isn't being removed.

**Considered:** making `findPackageRoot()` itself detect bundling and resolve correctly — rejected as not generally possible: a bundled consumer's JS no longer lives at its pre-bundle path, so there is no on-disk location left to walk up from that the library could discover on its own. The consumer is the only party that knows where it physically placed its own copy of the catalog assets.
