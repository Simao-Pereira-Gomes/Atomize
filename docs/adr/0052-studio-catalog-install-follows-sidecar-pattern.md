# Studio's Catalog install (Review step) follows the sidecar pattern, not a new CLI Bridge

Issue #134 ("Install to Catalog" action in the Templates Review step) was originally scoped against the pre-ADR-0038 architecture: "a typed CLI Bridge wrapper for `template install`... unit-tested with injected fake executors." That architecture no longer exists — `cli-bridge.ts` was deleted when Studio moved onto the sidecar model (ADR-0038, ADR-0042), and #133's Catalog remove already re-pointed the sibling capability at `atomize-core` directly (ADR-0049). Writing a new CLI Bridge wrapper for install would resurrect exactly the divergent-implementation problem that migration closed off, so the grilling session for #134 corrected the approach before implementation started.

**Decision:** Catalog install follows the same shape as #133's `catalog.remove`. `atomize-core`'s `TemplateLibrary.installTemplate`/`previewInstall` — already the CLI's own `template install` implementation — gains a third source shape (in-memory YAML content + name) alongside the existing file-path and HTTPS-URL sources in `resolveTemplateInstallSource`/`InstallTemplateInput`, wired to the already-existing but previously URL-only-reachable `TemplateCatalog.installFromContent`. This keeps `previewInstall`/`installTemplate` the single shared entry point — and single existence/collision check — for CLI-file, CLI-URL, and Studio-content installs. `atomize-sidecar/src/protocol.ts` gets a `catalog.install` RPC case, widening `SidecarTemplateLibrary`'s `Pick<TemplateLibrary, ...>` to include `installTemplate`/`previewInstall`. The Rust relay gets a `catalog_install_item` command mirroring `catalog_remove_item`, and `sidecar-client.ts` gets an `installCatalogItem` function on the same injectable-`SidecarInvoker`/fake-executor test pattern as `removeCatalogItem`.

On the Studio side: the install name is derived from the same `slugifyTemplateName(store["basic-info"].fields.name)` the Review step's Export filename already uses, with no separate name prompt. Scope (user/project) is chosen at install time. The action is available in both `ReviewSection.tsx` branches — fresh authoring and Open-Starting-Path sessions alike — gated the same as Export (`canReview`). For Open-Starting-Path sessions, `origin` is stripped before install, mirroring "Export as copy…"'s detach semantics (ADR-0037/0048): a Catalog item is a new canonical copy, not tied to the file it was opened from. A name collision surfaces a clear error with a simple Yes/No "Overwrite?" confirm — not Remove's type-to-confirm bar, since overwriting a Catalog item doesn't touch the user's own editor session or any prior export.

**Considered:** building the CLI Bridge wrapper as #134 literally described — rejected, it reintroduces the per-capability subprocess mechanism ADR-0038 retired everywhere else. Writing the composed YAML to a temp file and reusing the existing file-path install source — rejected as a workaround that pushes temp-file lifecycle management into Rust instead of giving install a real second source type. Having the sidecar call `TemplateCatalog.installFromContent` directly, bypassing `previewInstall`/`InstallTemplateInput` — rejected, it creates a second, divergent install entry point that skips `previewInstall`'s existence/collision check, which the sidecar would then have to reimplement itself. A type-to-confirm overwrite dialog matching Remove's — rejected as disproportionate: overwrite is recoverable in a way delete isn't, since the user's editor session and any prior export/save are untouched.
