# Studio sidecar wire protocol, correlation, and lifecycle

> Concretizes [ADR-0038](0038-atomize-core-shared-library-replaces-cli-subprocess.md), which established that Atomize Studio replaces its per-call CLI subprocess with a long-lived sidecar wrapping `atomize-core`, relayed through Rust over newline-delimited stdio — but left the message shape, correlation, lifecycle, and platform-build scope open. Issue #143 (the slice that proves this pipeline through Catalog template listing) flagged that protocol for a design review before it gets replicated to later capabilities (#144 Connection Profiles, #145 grounding).

**Decision:** a new workspace package `@sppg2001/atomize-sidecar` wraps `atomize-core`'s `TemplateLibrary`, compiled via `bun build --compile` to a standalone binary per Tauri's `externalBin` target-triple convention, with binaries built for macOS/Windows/Linux via a GitHub Actions CI matrix (one native job per OS/triple) rather than deferred to a single dev-machine triple or cross-compiled from one machine. Messages are a JSON-RPC 2.0-flavored envelope — `{jsonrpc, id, method, params}` requests, `{jsonrpc, id, result}` or `{jsonrpc, id, error: {code, message}}` responses — borrowing the envelope shape only, not full spec compliance: `error.code` is a string (`CATALOG_LIST_FAILED`, `METHOD_NOT_FOUND`, `PARSE_ERROR`, ...) rather than JSON-RPC's reserved numeric range, matching this codebase's existing named-error-class convention (`cli-bridge.ts`'s `CliAbsentError`/`CliVersionError`/etc.) over a spec neither side's hand-rolled implementation otherwise needs to honor. Methods use a dotted namespace (`catalog.list` for this slice; `connections.*`, `grounding.*` follow the same pattern as later issues add capabilities). Correlation `id` is a Rust-generated monotonically incrementing counter per app session, not a UUID and not sidecar-assigned. The sidecar dispatches requests concurrently — it does not block reading the next stdin line on a prior request completing — so responses may arrive out of order; this is the entire reason correlation ids exist rather than being vestigial, and it avoids a future slow call (grounding, Live Preview) queuing behind an unrelated one. The sidecar emits a no-`id` `sidecar.ready` notification once its request loop is live; the Rust relay waits for it before treating the process as usable, rather than assuming readiness after a fixed delay. Rust spawns the sidecar once at app launch, independent of the existing Atomize Studio CLI Gate's CLI-probe outcome — the two check unrelated things (an externally-installed CLI vs. a bundled binary), and CLI Gate is itself retired by #146, so sidecar lifecycle code was deliberately kept out of it to avoid coupling into code already scheduled for deletion. On unexpected exit, Rust restarts the sidecar, capped at 3 restarts within a 60-second window; beyond that it surfaces a new, dedicated fatal error state (distinct from CLI Probe Failure) with an in-app Retry action that resets the counter and attempts respawn, rather than requiring the user to relaunch Studio. On the frontend, a new `src/sidecar/sidecar-client.ts` module owns all companion-process calls, starting with `listCatalogTemplates()` (`invoke('catalog_list_templates')` → `catalog.list`); `cli-bridge.ts` loses `listCatalogTemplates` entirely rather than having it repointed in place, so `cli-bridge.ts` stays 100% subprocess-only and `sidecar-client.ts` 100% companion-process-only as the seam #144/#145/#146 cut along. Both sides get isolated protocol tests that avoid spawning a real process: the TS sidecar's request parsing, dispatch, and error serialization are driven by in-memory streams (mirroring `cli-bridge.test.ts`'s fake-executor pattern); the Rust relay's request encoding and id-correlation (including malformed-response and unknown-id handling) are driven by a mock reader/writer. Per #140's PRD, only the native backend's actual spawn/restart/kill glue and per-capability `tauri::command` wrappers are excluded from dedicated coverage, as thin glue better exercised manually.

**Considered:** a bespoke minimal envelope (`{id, command, payload}` / `{id, ok, data}`) — rejected in favor of the better-known JSON-RPC shape, which needs less scrutiny in the protocol review this ADR exists to close out. Sequential (non-concurrent) sidecar dispatch — rejected: it would make correlation ids pointless and serializes future slow calls behind each other. Unlimited restart retries — rejected: a crash-looping binary would retry forever with no user-visible signal. Folding sidecar health into the existing CLI Gate as a second launch precondition — rejected: couples new code into a component #146 removes shortly after. Numeric JSON-RPC-spec error codes — rejected: no off-the-shelf JSON-RPC tooling is in play to require spec compliance, and string codes match this repo's existing error-naming convention. Assuming sidecar readiness after a fixed delay instead of an explicit ready signal — rejected as a race condition wearing a timeout's clothes. Deferring the build to a single dev-machine triple, or cross-compiling all triples from one machine — rejected in favor of a full CI matrix now, even though nothing else in Studio is release-ready yet.
