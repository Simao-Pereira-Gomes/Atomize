# Studio Starting Paths gets a "Continue editing" banner for a draft parked by Back

ADR-0051 made Back non-destructive: leaving the Builder no longer discards the Authoring Store, only an explicit Discard does. That's correct as far as it goes, but it leaves a dead end once the history stack is exhausted — for example, Back out of the Builder into the Catalog Area, then Back again into Starting Paths. At that point `hasActiveDraft()` is still true (the store was never touched) but there is no history entry left to return to it, and clicking any Starting Path card only surfaces the "Discard your in-progress Template?" warning (ADR-0051's overwrite guard) with no way to see or resume what's being discarded. The draft becomes a ghost: alive in memory, invisible in the UI, reachable only through a warning that offers no third option besides losing it.

**Decision:** `StartingPathPicker` shows a "Continue your in-progress Template" banner — naming the draft via its Basic Info name — whenever `hasActiveDraft()` is true, regardless of history stack state. Its "Continue editing" action (`StudioShell`'s new `resumeDraft`) re-enters the Builder exactly the way `goBack` would — pushing the current state onto the history stack and flipping `surface` to `"builder"` — without touching the Authoring Store. This isn't the "Forward control" ADR-0051 rejected: Forward would replay whatever was popped in stack order; this is a single, always-available path back to the one thing that can otherwise become unreachable — the live draft itself.

**Considered:** making the sidebar's already-active "Templates" button resume the draft on click, instead of its current no-op — rejected as too undiscoverable; clicking a nav item that's already highlighted as active isn't something a user reaches for. Preventing Back from ever exhausting the stack while a draft is active — rejected as unnecessary and inconsistent with ADR-0051's non-destructive Back everywhere else; the fix only needed a way back in, not a constraint on getting out.
