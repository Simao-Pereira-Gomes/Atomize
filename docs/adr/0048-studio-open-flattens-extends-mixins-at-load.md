# Studio's Open flattens extends/mixins at load time; origin persists across Save, stripped only on Export as copy

Supersedes [ADR-0037](0037-local-file-clone-omits-origin.md). ADR-0037's Local File Clone stripped `origin` — alongside `extends`/`mixins` — unconditionally at entry, before issue #135 was revised to merge Local File Clone and Open into a single Starting Path, Open, whose copy-vs-in-place behavior is decided at save time (Save vs. Export as copy) rather than at entry.

The first pass of that merge ported ADR-0037's field list forward but moved *all* of it — `extends`, `mixins`, and `origin` alike — to strip only on Export as copy, leaving `Save` (write back to the original path) preserve a file's declared `extends`/`mixins` untouched. That turns out to be unsafe. `atomize-core`'s `TemplateComposer.resolve()` (`packages/atomize-core/src/templates/composer.ts`) merges a parent's tasks, mixin tasks, and the child's own tasks into one combined `tasks` array via `mergeTemplates(intermediate, raw)` — "child fields always win" — but that merge leaves the child's own `extends`/`mixins` fields present in the composed result; it does not clear them. Studio only ever edits the composed view (that's the entire point of resolving `extends`/`mixins` before loading — see the "New capability" section of issue #135), so `Save` must write back a `tasks` array that already contains the parent's and mixins' contributions inlined. A file saved that way while still declaring `extends: parent` would re-compose on its next open — in Studio or via the CLI — merging the parent's tasks in a second time on top of a list that already contains them once. Each open-edit-save cycle through Studio would inflate such a file further: silent, cumulative corruption, not merely staleness.

**Decision:** Studio's Local File Loader resolves `extends`/`mixins` into their composed form immediately at load time — before classification (`valid`/`malformed`/`wrong-format`) runs — via a new sidecar operation wrapping `atomize-core`'s `TemplateLibrary.getRunnableTemplate(path, { validate: false })`, and strips the now-redundant `extends`/`mixins` fields from the loaded Template at that same point. This applies uniformly regardless of which save action is eventually used: `Save` (write back to the original path) and `Export as copy…` (write to a new path) both operate on an already-flat Template, so neither can reintroduce the duplication risk above.

`origin` is treated differently, because it carries no equivalent risk: nothing re-resolves off it, so leaving it declared has no functional consequence, only an informational one. `origin` is preserved through loading and through `Save`, continuing whatever history the source file already recorded. It is stripped only by `Export as copy…`, matching ADR-0037's original reasoning that a newly detached copy should not claim a Catalog-traceable relationship it no longer tracks.

A consequence: opening a Template that uses `extends`/`mixins` in Studio and saving it — even in place, even for a single trivial edit — permanently detaches it from its parent/mixins the first time. The file keeps its identity (same path), but stops being a live reference to its parent; unlike an un-opened `extends`-based file, it will not pick up later changes to that parent the next time it's resolved. This is an accepted trade-off of composing eagerly so Studio can present and let the user edit the full, real task list, not an oversight.

**Considered:** deferring `extends`/`mixins` stripping to `Export as copy…` only, matching ADR-0037's original field list exactly and leaving `Save` a byte-for-byte round trip whenever no field actually changes — rejected once the composer's merge behavior above was traced through: `Save` must write back the composed `tasks` array for in-app edits to be visible at all, so a `Save` that also kept `extends`/`mixins` declared would guarantee double-composition on the file's next open, not merely risk it. Re-deriving a minimal `extends`/`mixins`-preserving diff on save — write back only the fields the user actually edited, leaving inherited fields declared rather than inlined — rejected as substantially more scope than this issue: it would require Studio to track, per field, whether it came from the parent/mixins or the child through arbitrary user edits, a capability neither the Authoring Store nor `atomize-core`'s composer expose today. Stripping `origin` at load time too, for symmetry with `extends`/`mixins` — rejected: `origin` has no re-resolution risk, so treating it identically would only lose information (a file's own recorded lineage) for no safety benefit.
